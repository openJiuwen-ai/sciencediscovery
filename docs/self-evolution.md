# 自演进（RSI）设计方案 —— 用户视角

本文从**用户能看到、能操作、能负责**的角度设计 Science Agent 的自演进能力。后端由
[AgentDescent](https://github.com/Birfy/agentdescent) 承担并行演进循环（ledger → workers →
aggregator → commit），Node 控制面继续持有治理、执行与溯源。技术接缝在第 11 节。

---

## 1. 一句话

> 让 Agent 把「你纠正过它的每一次」变成**可审计、可回滚、被证明有效**的技能版本，
> 而不是让用户反复在每个新会话里重复同样的叮嘱。

---

## 2. 用户是谁：三个真实场景

Science Agent 的用户是做实际分析的科研人员，不是想「训练一个 Agent」的工程师。
自演进必须回答的是他们的三个具体痛点：

| # | 场景 | 今天的体验 | 自演进之后 |
|---|---|---|---|
| A | **重复叮嘱**：每次都要提醒"多重比较要做 BH 校正""图要标 n 和误差棒" | 每个新会话重说一遍，或手工改 SKILL.md | 说一次 → 系统提议把它写进技能 → 在你的历史题目上验证有效 → 采纳 |
| B | **同类任务反复做**：这个月做了 7 次同构的差异表达分析 | 每次从零编排，质量看运气 | 系统识别出重复模式，提议固化为一个新技能，并给出「用它 vs 不用它」的对照分数 |
| C | **改了不知道有没有变好**：手工改了技能提示，凭感觉 | 无法验证，改坏了也不知道 | 任何改动都在留出题集上跑对照，给出 Δ 与有效概率，先影子试用再转正 |

**产品定位由此确定**：不是"RSI 训练控制台"，是**「Agent 的经验积累与版本管理」**。
训练看板是给进阶用户的第二层，不是入口。

## 3. 术语翻译（对用户不出现 RSI 黑话）

| AgentDescent | 用户看到的词 | 说明 |
|---|---|---|
| `Evolvable` artifact | **可演进资产** | 技能、评审准则、专家提示 |
| `Task` / dataset | **题集（Task set）** | 从历史会话转化而来 |
| `reward` | **评分口径** | 用户定义"什么算做对了" |
| `Diff` + `EvidenceCard` | **改动建议 + 证据卡** | 改了什么 + 凭什么说它更好 |
| aggregator merge | **采纳** | |
| `P(Δ>0) > 1−δ` (Beta 后验) | **有效概率 92%** | 不暴露 Beta/δ |
| held-out reward | **留出题得分** | train/holdout 显式画出来 |
| dev / stable 双分支 | **试用版 / 正式版** | 影子模式 → 转正 |
| blast radius L0/L1/L2 | **改动范围：底座（不可改）/ 骨架（需批准）/ 技能（可自动）** | |
| staleness / async | 不暴露 | 只在高级设置里一个「并行度」滑杆 |

## 4. 交互 → 演进：桥接层（本方案的核心）

AgentDescent 假设「一个固定数据集 + 一个可自动计算的 reward + 可任意重跑的 rollout」。
真实用户交互一条都不满足。这个落差是整套方案唯一真正难的地方，必须正面解决。

### 4.1 落差的准确形状

| AgentDescent 需要 | 用户交互实际是 | 后果 |
|---|---|---|
| N 个任务 | 1 个任务，一次性 | 没有 batch，接受门没有样本量 |
| 固定任务分布 | 每次分析都不一样，长尾、几乎不重复 | 攒不出「同类题」 |
| 可自动算的 reward | 好坏只有用户知道，且多数时候不明说 | 没有梯度 |
| rollout 可重跑可丢弃 | 用户这次运行是真实产出，不能"为训练重跑一遍" | 不能在线采样 |
| 留出集做无偏验证 | 没有留出集 | 无法判断是否真的变好 |
| 离线、分钟~小时 | 在线、同步、用户在等 | 不能占用交互路径 |

### 4.2 关键转向：交互不产生"样本"，交互产生"环境"

不要试图把一次会话变成 dataset 的一行。**把它变成一个可被无限重放的仿真环境**：

```
一次真实会话结束后，自动沉淀出一个 Episode（可复盘案例）：
   ├─ 题面      = 用户当时的原始问题
   ├─ 输入      = 工作区输入文件的 CAS 快照
   ├─ 基线      = 用户实际收到、并且实际接受/纠正过的那次产出与轨迹  ← 关键
   ├─ 信号      = 用户的显式与隐式反馈
   └─ 标签      = 触发了哪些技能、命中了哪些失败模式
```

**「基线」这一项解决了两个最难的问题**：

- **没有 gold answer** → 不需要。有 baseline 就能做**成对比较**（pairwise）：
  候选版本重跑同一个 episode 得到 B，判「B 比用户当初收到的 A 好 / 一样 / 差」。
  pairwise 判断比给绝对分数可靠得多，而且完全不需要标准答案。
  映射到 AgentDescent 的 `reward → [0,1]` 干净利落：**赢 = 1.0，平 = 0.5，输 = 0.0**。
- **只有一个样本** → 一个 episode 可以被重放任意多次（不同候选、不同随机性），
  一次交互因此放大成 K 个可比较的 rollout。dataset 不是"攒"出来的，是**从环境里采样**出来的。

> 一句话：**用户的历史会话是免费的、可重放的仿真环境；用户当初收到的答案是免费的 baseline。**

### 4.3 三个时间尺度必须分开

这是在线/离线的切分线，也是"不能占用用户交互路径"的答案：

| 尺度 | 时机 | 做什么 | 用不用 AgentDescent |
|---|---|---|---|
| **T0 在线** | 用户这一轮，秒级 | **只取用，不演进**：检索相关经验注入上下文 | 否（纯 retrieval） |
| **T1 会话后** | 会话结束，分钟级 | 沉淀 Episode、抽取失败模式、记经验候选。**不改任何东西** | 否 |
| **T2 离线** | 攒够了，天~周级 | 真正的 `evolve()`：并行重放、成对判分、留出验证、接受门 | 是 |

**T0 永不跑 rollout**。用户在等结果的路径上一次模型调用都不额外加。
演进任务在用户开始新会话时立刻让出执行槽——「仅在空闲时演进」是**默认且强制**，不是可选项。

### 4.4 按"口径"聚类，而不是按"任务"聚类

最真实的反驳是：用户的任务几乎不重复，8 道同类题永远攒不出来。

**解法是换聚类维度。** dataset 的一行不必是「一个完整科研任务」，
而是**「一个触发了同一条规矩的检查点」**：

```
❌ 按任务聚类：8 次"差异表达分析"    → 用户一辈子也攒不到
✅ 按口径聚类：8 次"用了统计检验但没做多重比较校正"
              （题面各不相同：转录组、代谢组、临床表、蛋白定量…）
```

**题面多样、口径共享**。这个粒度上 dataset 是攒得出来的，而且**多样性反而是优点**——
学到的规则被迫是通用的，不会过拟合到某一类分析。

这正好对上 AgentDescent 的 `KeyedRules`：一条规则一个 key，一个 key 对应一族触发它的 episode。
产品上这个对象叫**题族（Task family）**：

```
Episode（一次会话沉淀）  ──按失败模式打标──▶  题族（共享评分口径）  ──样本数达阈值──▶  evolve()
```

### 4.5 冷启动：第一天就有价值，不是"攒够 8 题之前什么都没有"

用户体验必须是连续的，所以经验有**两级形态**，自动升级：

| 形态 | 触发 | 生效方式 | 强度 |
|---|---|---|---|
| **便签（Note）** | 用户说一次 | T0 检索注入上下文，**立刻生效** | 未经验证，随时可删 |
| **技能改动（Diff）** | 该便签所属题族攒够 ≥8 个 episode | 走完整演进 + 留出验证 + 接受门 | 已证明有效，进版本时间线 |

用户看到的是同一条经验在**升级**：

```
「以后先做 BH 校正再报显著性」
  Day 1   便签 · 本项目生效 · 未验证                    ← 立刻有用
  Day 12  已收集 9 个相关案例，可以验证了  [开始验证]
  Day 12  ✅ 留出 Δ=+0.13，有效概率 92%  → 写入技能 v8（试用版）
  Day 19  影子 5/5 无回归  → 转正
```

这条升级路径是整个产品可用性的关键：**没有它，用户在第一个月里得不到任何东西，也就不会去攒数据。**

### 4.6 在线演进的唯一例外：轻量决策点

重任务（要跑代码、要检索、要写报告）在线跑 N 路候选太贵太慢，一律离线。
但**纯文本的轻量决策点**可以在线做 best-of-N，即时生效且样本免费：

- 「这批数据该用哪个统计检验」
- 「检索 PubMed 该用什么查询式」
- 「这段结论该标哪几条证据」

这类决策一次调用几百 token，跑 3 路 + 一次 pairwise 判优是可接受的，
而且**判优结果直接就是训练信号**。建议作为 M3 的可选项，默认关。

### 4.7 桥接层小结

```
     用户交互（T0）                     沉淀（T1）                  演进（T2）
  ┌──────────────┐   会话结束    ┌──────────────┐  按失败模式  ┌──────────────┐
  │ 检索经验注入  │ ───────────▶ │  Episode 池   │ ──打标聚类─▶ │   题族        │
  │ 便签立刻生效  │              │ 题面+输入+基线 │             │ 共享评分口径   │
  │ 零额外开销    │              │ +用户信号     │             │ train/holdout │
  └──────────────┘              └──────────────┘             └───────┬──────┘
         ▲                                                           │ ≥8 样本
         │                                                           ▼
         │                                                   ┌──────────────┐
         └────────── 采纳后回流（新技能 revision / 便签）──────│ AgentDescent │
                                                              │  并行重放     │
                                                              │  成对判分     │
                                                              │  接受门       │
                                                              └──────────────┘
```

**AgentDescent 不接在用户交互上，接在 Episode 池上。** 中间隔着沉淀与聚类两步，
这两步才是本方案要自己写的东西。

### 4.8 题族的三种来源：沉淀之外，用户也可以直接给数据集

上面讲的是"从交互里长出题集"。但**用户手上本来就有数据的情况必须一等公民地支持**——
它不是备选方案，而是解决冷启动最快的一条，也是**你自己开发和验证整条演进链路的唯一手段**
（没有它，功能写完了却没有任何数据可以跑）。

关键在于：**三种来源产出的是同一个对象（题族），只是 badge 不同**，不是三套系统。

| 来源 | 用户拿什么进来 | 基线 / 评分口径 | 现实性 |
|---|---|---|---|
| **① 会话沉淀** | 什么都不用做（§4.2） | 用户当初收到的产出 = 基线，成对比较 | 最贴合真实分布，但要等 |
| **② 用户导入** | 见下面四种形态 | 视形态而定 | **冷启动最快**，且是唯一能立刻 dogfood 的 |
| **③ 公开 benchmark** | HF 数据集名（AgentDescent `dataloader` 直接支持，零依赖） | 数据集自带 gold | 分布不匹配，**只当护栏，不当目标** |

#### ② 用户导入的四种形态（按现实性排序，不是按技术难度）

| 形态 | 用户提供 | 评分口径 | 谁会有 |
|---|---|---|---|
| **B. 输入 + 已认可的结果**（推荐） | 一批"原始数据 → 我当初做出来并认可的报告/结果表"配对 | 已认可结果 = 基线，**直接复用成对比较**，零额外标注 | 几乎所有课题组的归档里都有 —— **这是被严重低估的一座金矿** |
| **C. 一批输入 + 一份验收标准** | 20 个 CSV + 一份 checklist（"必须报 n、必须做校正、必须标单位"） | checklist 作为 judge 维度，绝对打分 | 有 SOP 的实验室 |
| **A. 标准题集** | CSV/JSONL，prompt 列 + gold 列 | 精确匹配 / 包含 / 数值容差 | 少数（这是 ML 人的数据形态，不是科研人的） |
| **D. 只有输入，没有答案** | 一个目录，每个子目录一道题 | 只能用默认自动信号（硬门 + 溯源 + Reviewer），或用户先跑一遍再认可（→ 退化成 B） | 兜底 |

**形态 B 是这条路径的重点**，因为它把 §4.2 的洞察从"ScienceAgent 的会话历史"
扩展到了"用户在装 ScienceAgent 之前的全部工作积累"。用户视角是一句很好懂的话：

> 「把你过去做过的 20 份分析扔进来，让 Agent 学会按你的路子做。」

#### 导入的交互

```
【导入题族】
  ├─ 拖入 CSV / JSONL        → 列映射（题面列 / 标准答案列 / 输入文件列）
  ├─ 拖入一个目录             → 每个子目录 = 一道题，目录内文件 = fixtures
  ├─ 填一个 HF 数据集名       → 走 AgentDescent dataloader，直接可用
  └─ 从既往会话批量导入        → 来源 ①，勾选即可
              ↓
       预览前 3 道题（题面 + fixtures + 该口径下的试评分）
              ↓
       口径选择 + train/holdout 划分 + 健康度诊断（同 §6.2）
```

预览时**必须先试评 3 道题再让用户点确认**——列映射错、口径选错是导入最常见的失败，
而这两种错都要跑完一整轮昂贵演进才会暴露。

#### 三条必须成文的护栏

1. **holdout 不能是合成的**。允许从一个 episode 扩增出变体来补训练样本量，
   但留出集只能来自真实来源，且导入的数据集要在 UI 上标明来源 badge。
2. **导入数据集可以当训练集，转正必须过真实回归**。
   在 PubMedQA 上学到的东西未必对用户的 CSV 分析有用，甚至有害。
   规则：**任何版本要从"试用"转"正式"，必须在来源 ① 的真实 episode 池上不回归**——
   即使它是在导入数据集上学到的。没有真实 episode 时，只能停在试用版。
3. **公开 benchmark 只做护栏**。它的作用是"确认演进没有把通用能力搞坏"，
   不是"在 benchmark 上刷分"。UI 上把它放在"回归检查"而不是"训练题族"里。

#### 对交付节奏的影响

这条路径**技术上就是 AgentDescent 的 quickstart**（`tasks_from` + `evolve_skill_dir`），
是整套方案里最薄的一层。所以它应当**和 M1 一起发**，而不是等 M0 攒够数据：

- 对用户：手上有归档的人第一天就能跑通完整链路，不用等一个月
- 对你：这是唯一能在没有真实用户历史的情况下**端到端验证演进链路**的方式

## 5. 四条用户路径（成本递增，价值递增）

### 路径 A —— 零配置：一句纠正就是一次学习

```
会话中 → 用户说「以后先做 BH 校正再报显著性」或点某轮的 👎 + 一句话
              ↓
       系统记为一条【经验候选 Lesson】（附该轮的 CAS 引用作为出处）
              ↓
   Composer 上方出现轻量徽章：「有 3 条待学习的经验」
              ↓
   点开 → 选择作用范围（本会话 / 本项目 / 全局）→ 「学习」
              ↓
   后台一次小规模演进：把相关历史会话作为题目验证这条经验是否真的提升
              ↓
   成功 → 技能新 revision（标注来源：Lesson #12）；失败 → 明确告诉用户
            「这条经验在你的 8 道题上没有带来提升，已保留为备注而未写入技能」
```

**关键设计**：不能"用户说什么就往 SKILL.md 里塞"——那会让技能提示无限膨胀且互相打架。
经验必须通过接受门才写入。这正是用 AgentDescent 而不是简单 append 的理由，
也是给用户的诚实反馈：**有些叮嘱其实没用**。

### 路径 B —— 主路径：会话 → 题集 → 演进 → 采纳

```
任一历史会话 → 【加入题集】按钮
      ├─ 题面 = 用户当时的原始问题
      ├─ 输入 = 该会话工作区输入文件的 CAS 快照（可复现）
      └─ 评分口径 = 四选一（见第 7 节）
                          ↓
        题集页：题目数、train/holdout 划分、口径分布直方图
        （< 8 题时明确提示「样本太少，结论不可信」并禁用自动采纳）
                          ↓
        选择要演进的资产（某个技能 / 某个评审准则）→ 【开始演进】
                          ↓
        演进看板：得分曲线、每个 worker 的 rollout、成本累计、随时 Stop
                          ↓
        【待采纳改动】队列：diff + 证据卡 + 留出题 Δ + 有效概率 + 影响范围
                          ↓
        批准 → 新 revision 进入【试用版】→ 影子无回归 K 次 → 提示转正
```

### 路径 B' —— 自带数据：导入题族，当天就能演进

给手上已有归档的用户（见 §4.8）。与路径 B 汇合于同一个「题族」对象：

```
【导入题族】拖入 20 份「原始数据 → 我当初认可的报告」配对
              ↓
   自动列映射 + 预览前 3 道题的试评分（避免映射错误跑完才发现）
              ↓
   口径默认「成对比较」——已认可的报告就是基线，零标注
              ↓
        与路径 B 完全相同的演进 → 提案 → 采纳 → 试用版
              ↓
   ⚠️ 转正闸门：必须在真实 episode 池上不回归；没有真实 episode 则停在试用版
```

**这是冷启动最快的一条**：不需要等一个月攒交互，用户装上当天就能把
「我过去是怎么做分析的」教给 Agent。

### 路径 C —— 进阶：夜间自动演进

系统配置里开启：题集、资产、预算上限（费用/时长/并发）、计划时间。
夜里跑，**只提交到试用通道**，早上给用户一个待审列表 + 一封「昨夜学到了什么」的摘要卡。
用户永远是最后一道闸。

## 6. 界面设计

### 6.1 入口位置

- **系统配置 → Self-evolution**：总开关（默认关）、演进模型、预算、治理默认值、演进期权限策略。
  与现有 Skills / Permissions / Reviewer 平级，遵循 Global → Project → Session 继承。
- **工作台左侧新增「Evolution」面板**（开关打开后出现），三个 tab：题集 / 运行 / 待采纳。
- **会话内轻量入口**：Composer 上方的「经验徽章」、每轮消息的 👍👎、会话头部的「加入题集」。
- **Skill 详情页新增「版本时间线」**（见 6.5）。

### 6.2 题集（Task sets）

一张表 + 一个健康度面板：

| 列 | 内容 |
|---|---|
| 题面 | 用户原始问题（可编辑） |
| 来源 | 会话链接 / 上传 / 合成 |
| 输入快照 | 文件数 + 大小，可预览 |
| 评分口径 | 见第 7 节，题集级默认 + 可按题覆盖 |
| 划分 | train / holdout（默认 7:3，可锁定某些题永远在 holdout） |
| 最近得分 | 当前正式版在这题上的分数 |

**健康度面板（这是用户真正需要的诊断）：**
- 分数分布直方图 —— 全是 1.0 或全是 0.0 → 提示「口径没有区分度，演进学不到东西」
- 方差 / 重跑一致性 —— 同一题跑两次分数差很大 → 提示「评分不稳定，结论会是噪声」
- 题目相似度聚类 —— 8 题里 6 题几乎一样 → 提示「有效题目其实只有 3 道」

### 6.3 演进运行看板（Run）

给进阶用户，但要让普通用户看一眼就懂：

- **主图**：train / holdout 两条得分曲线（holdout 是唯一可信的那条，视觉上加粗）
- **Worker 泳道**：每个并行 worker 当前在跑哪道题、耗时、成功/失败
- **采纳流水**：每一次 aggregator step 的结果 —— 采纳 / 拒绝（原因：留出未提升 / 冲突 / 超出信任域 / oracle 否决）
- **成本条**：已用 token 与费用 / 上限，超限自动停并保留断点
- **随时 Stop**：复用现有 Stop run 的中止贯通链路

### 6.4 待采纳改动（Proposals）—— 最重要的一屏

每条提案是一张卡：

```
┌──────────────────────────────────────────────────────────┐
│ 技能 result-evaluator · 影响范围：技能（可自动采纳）        │
│                                                          │
│  [diff 视图]  + 报告显著性前必须先做 BH 多重比较校正…       │
│                                                          │
│  证据卡                                                   │
│   · 题 #3「差异表达 top50」   0.20 → 0.90                  │
│   · 题 #7「批次效应分析」     0.55 → 0.85                  │
│   · 留出题整体 Δ = +0.13    有效概率 92%                   │
│   · 无回归：其余 12 道题分数未下降                          │
│                                                          │
│  来源：题集「转录组分析 v1」· 运行 #24 · 2 名 worker        │
│                                                          │
│  [ 批准并试用 ]  [ 拒绝 ]  [ 永久否决此类改动 ]  [ 看完整 diff ] │
└──────────────────────────────────────────────────────────┘
```

- **拒绝**要能带一句理由，理由回流为下一轮的 propose 上下文（负反馈也是信号）。
- **永久否决**写入项目级否决表，同类 diff 不再出现（避免反复骚扰）。
- 「影响范围」直接决定按钮：技能级可开自动采纳；骨架级强制人工批准；底座级根本不会出现在这里。

### 6.5 版本时间线 · 影子模式 · 回滚

技能详情页把**手工编辑的 revision** 和**演进产生的 revision** 混排在一条时间线上
（ScienceAgent 本来就有不可变 revision + 包哈希，这里几乎是免费的）：

```
v7  正式版  ← 手工编辑            2026-07-02
v8  试用版  ← 演进 #24  留出 +0.13  已影子运行 3/5 次，无回归   [立即转正] [回滚]
```

- **影子模式（Shadow）**：试用版不影响用户当前输出，只在后台对新会话再跑一次评分对照。
  累计 K 次无回归后弹「可以转正了」。对应 AgentDescent 的 dev→stable 提升，
  对用户的意义是**零风险试用**。
- **回滚**是一等公民：任意版本一键设为正式版，并显示"回滚会丢掉这几条已学经验"。

### 6.6 技能发现（场景 B 的落点）

当系统在会话历史里发现 ≥N 个同构任务且没有对应技能时，在 Evolution 面板给出建议卡：
「你做过 7 次结构相似的分析，要不要固化成技能『批量差异表达报告』？」
→ 用这 7 个会话直接生成题集并起草技能，走同一条采纳流程。

## 7. 评分口径：用户怎么定义"好"

**这是整套方案的成败点**。没有可信的 reward，演进就是在噪声上过拟合。
Science Agent 的优势是**已有大量可复用的自动信号**，用户不必标注：

| 口径 | 信号来源（已存在） | 用户成本 | 适用 |
|---|---|---|---|
| **成对比较（默认）** | 与该 episode 的**基线产出**逐项对比（§4.2）：硬门先判，再由 judge 模型判"哪个更好" | 零 | 绝大多数分析任务 |
| **绝对打分** | 硬门：执行 exitCode + 产物存在；溯源：claims/evidence 链完整率、Citation 检查；语义：Reviewer findings | 零 | 需要跨题族横向比较时 |
| **验收清单** | 复用 `result-evaluator` 的 6 维（准确/完整/稳健/相关/方法学/批判性）作为 judge 维度 | 勾选几项 | 需要方法学严谨度时 |
| **自定义检查脚本** | 用户写的 Python check，在现有 bubblewrap 沙箱里跑，返回 0~1 | 会写代码 | 硬指标（如 RMSE 阈值） |

**为什么默认是成对比较**：绝对打分需要一把校准过的尺子，而 LLM 打绝对分在科研任务上
既不稳定也不可比；成对比较只需要回答"A 和 B 哪个更好"，一致性高得多，
而且 §4.2 已经保证了**每个 episode 天生自带 baseline**，不需要用户提供任何标准答案。

```
reward(candidate) =
    0  ─ 若硬门未过（执行失败 / 产物缺失 / 溯源链断裂）        ← 硬门优先，不进 judge
    否则 pairwise(baseline, candidate)：  赢 1.0 / 平 0.5 / 输 0.0
         judge 维度 = 用户在题族上勾选的验收清单
         判两遍并交换 A/B 顺序以消除位置偏好，不一致则记为平局
```

**用户可见的诚实提示**：口径选定后立刻在已有 episode 上算一遍分布 ——
若"平局"占比 > 80%，说明这个口径分辨不出好坏，直接提示用户加维度或换口径，
而不是让他跑一次昂贵且注定学不到东西的演进。

## 8. 治理与安全（用户视角的三层）

直接把 AgentDescent 的 L0/L1/L2 翻译成用户能判断的语言，并复用现有权限体系：

| 层 | 包含什么 | 用户看到的 | 合并方式 |
|---|---|---|---|
| **底座（L0，冻结）** | 权限系统、沙箱与 bubblewrap 策略、审批逻辑、CAS/溯源、模型密钥、评分口径本身、演进预算 | 设置页里**灰掉并注明"自演进永远无法修改"** | 不可写 |
| **骨架（L1，需批准）** | Reviewer 准则、specialist / 子代理提示、编排策略、**内置技能** | 提案卡强制人工点批准（oracle = 用户或更强模型） | 串行 + 强制 oracle |
| **技能（L2，可自动）** | 用户自建技能、项目经验库 | 可开「自动采纳」，仍留审计与一键回滚 | 留出分数门控后自动合并 |

**演进期的权限策略（必须显式设计）**：rollout 是**无人值守**的，绝不能弹权限卡片等一个不在场的用户。
设置页给一条独立配置，默认：

> 演进运行时：允许工作区内代码执行与**已授权**的连接器；任何新的权限请求一律拒绝并记为该题失败。

同时演进产生的所有 rollout 会话标记为 `ephemeral`，不进用户的 Session 列表，跑完销毁工作区，
但 Prompt Manifest / 执行记录照常入 CAS（可审计）。

**评分口径不可自我修改**是 L0 里最容易被忽略的一条：如果允许演进改 reward，
系统会学会"让自己得高分"而不是"做得更好"。UI 上要明说这条。

## 9. 成本与资源：必须对用户诚实的两件事

### 9.1 费用

演进 = 题数 × 轮数 × worker 数 次完整 Agent 运行，**比一次聊天贵一到两个数量级**。

- 开始前给**预估**：「约 120 次运行，预计 ¥XX ~ ¥YY，预计 40 分钟」
- 运行中实时累计，复用现有 Usage 页面，按运行归集
- 硬上限（费用 / 时长 / 运行次数）任一触顶自动停，ledger 保留断点可续跑
- 建议默认：rollout 用主力模型，**反思/提案用便宜模型**（AgentDescent 的 `reflect_with` 正是为此）

### 9.2 并发的真实约束（不要给用户假承诺）

Runner 目前是**单一全局执行 worker**。所以 `n_workers=4` 的并行 rollout 会在 runner 处排队，
用户会看到"并行了但没变快"。方案：

- 演进并发默认 **2**，设置项旁直说「演进会与你的交互式会话抢执行槽」
- 提供「仅在空闲时演进」开关（无活跃会话运行时才调度）
- 中期把演进 rollout 接到 AgentDescent 的 `SandboxPool`（共享 lease、一个上限跨进程），
  与 runner 队列共用同一个天花板，而不是两套各自为政

## 10. 失败与边界情形的用户体验

| 情况 | 用户看到 |
|---|---|
| 题目 < 8 | 「样本太少，结论不可信」；允许跑但禁用自动采纳，提案卡标注低置信 |
| 口径无区分度 | 演进拒绝启动，直接给出直方图和修改建议 |
| 连续 N 轮无采纳 | 自动停止：「在当前口径下已达上限，继续投入不会更好」——这是**正确结果**，不是失败 |
| 提案让留出分下降 | 根本不会进入待采纳队列；在运行看板的"采纳流水"里显示为已拒绝及原因 |
| 预算/时间耗尽 | 保留 ledger 断点，一键续跑 |
| 模型 API 不可用 | 已完成的 rollout 不浪费，evidence 结算回池 |
| 用户回滚 | 明确列出"这会丢掉哪几条已学经验"，并保留它们在经验库中可再次学习 |

## 11. 后端落点（与现有架构的接缝）

保持仓库既有原则不变：**Python 跑循环，Node 管治理与真实执行**。

```
                浏览器 :4310
                     │
        ┌────────────▼──────────────┐
        │  services/api (Node)      │  题集/运行/提案存储、治理、
        │                           │  提案→技能 revision 落盘、成本记账
        └───┬──────────────────┬────┘
   POST /evolve                │ 反向回调（与 gateway 的 tool-exec 同构）
            │                  │  · run(candidate, task)   → 起一次 ephemeral run
            ▼                  │  · reward(task, output)   → 复用 Reviewer/溯源检查
   ┌────────────────────┐      │  · propose(...)           → 便宜模型反思
   │ services/evolve    │──────┘
   │ (Python, 回环)      │
   │  agentdescent:      │
   │   evolve_skill_dir  │      ledger（git-backed）落 data/evolution/ledger/
   │   evolve() / async  │      随数据目录整体备份
   └────────────────────┘
```

要点：

1. **新增一个回环侧车 `services/evolve`**，形态与 gateway 完全一致（uv 项目、只绑 127.0.0.1、无会话状态）。
2. AgentDescent 的三个回调 `run` / `reward` / `propose` 实现为**对 Node API 的 HTTP 回调**，
   与 gateway 的 `/internal/tool-exec` 同构 —— 沙箱、权限、溯源仍然只在 Node 侧发生。
3. **技能目录演进直接对上 `evolve_skill_dir`**：state key 是文件路径，
   两个 worker 改不同文件自动 fuse，改同一文件按留出分裁决。
   产物写回成 ScienceAgent 已有的**不可变 skill revision** —— 两边的数据模型天然对齐。
4. 骨架级（specialist / 评审准则）用 `evolve_agent_dir`（L1，强制 oracle）。
5. `frozen=` 参数把安全相关文件锁死，与 L0 清单一一对应。
6. 证据卡、留出 Δ、有效概率来自 `EvolutionResult` / `RoundInfo`，直接映射到提案卡字段。

## 12. 分阶段交付

桥接层（§4）决定了阶段划分：**先能沉淀，才谈得上演进**。

| 阶段 | 交付 | 用户可感知的价值 |
|---|---|---|
| **M0 —— 沉淀层（不含 AgentDescent）** | 便签捕获与 T0 检索注入 · Episode 自动沉淀（题面/输入快照/基线/信号）· 失败模式打标与题族聚合 · 题族健康度页 | 「它记得我上次说的」——第一天就有效果，且开始默默攒环境 |
| **M1 —— 第一次演进** | **题族导入（§4.8：CSV/目录/HF/会话批量）** · 手工触发的单技能同步演进（n_workers=2，仅 L2）· 成对比较口径 · 提案审批 · 版本时间线与回滚 · 预算上限 | 「我把过去 20 份分析扔进去，它学会了按我的路子做」 |
| **M2 —— 放手** | 便签→提案自动升级 · 影子模式与转正 · 夜间计划演进 · 口径编辑器 · 成本预估 · SandboxPool 接管并发 | 「晚上它自己学，早上我审」 |
| **M3 —— 更深的自演进** | 骨架级演进（Reviewer 准则 / specialist / 编排）+ oracle 审批 · 异步 barrier-free · 技能发现 · 在线轻量决策点 best-of-N（§4.6） · 跨项目经验迁移 | 「它开始改进自己判断好坏的方式了」——也是必须最谨慎的一步 |

**M0 单独就有产品价值**（相当于一个带出处的项目级记忆），而 M1 里的**题族导入（§4.8）
是 M0 的解耦阀**：有了它，即使 M0 还没攒出足够 episode，你和用户也都能立刻端到端跑通演进。
没有它，M1 会陷入"功能写完了但没数据可跑"的死锁。

两条来源的分工要清楚：**导入的数据集负责让链路跑起来，沉淀的 episode 负责让结论可信**
（转正闸门只认后者，见 §4.8 护栏 2）。

每个阶段独立可用，前一阶段不做完不进下一阶段。

## 13. 需要拍板的决策

1. **默认作用域**：学到的经验默认落在 **Project** 层（复用现有三层继承）还是 Global？
   建议 Project —— 不同课题的规矩不该互相污染。
2. **自动采纳的默认值**：L2 技能默认自动采纳，还是一律人工批准？
   建议**默认人工**，用户跑顺三次后主动开自动 —— 信任要挣。
3. **内置技能算 L1 还是 L2**：内置技能被所有会话使用，blast radius 天然高。
   建议内置技能演进产出的是**用户侧 fork**（不改仓库内置件），这样 M1 就不用碰 L1。
4. **Reviewer 是否作为默认 reward**：Reviewer Specialist 目前默认关闭。
   若作为默认口径，需要在开启自演进时一并要求开启 Reviewer，用户要知道这会增加模型调用。
5. **ephemeral rollout 会话的可见性**：完全不可见，还是在运行看板里可展开查看某次 rollout 的完整对话？
   建议**可展开**——调试演进为什么没学到东西时，这是唯一有用的东西。
6. **Episode 沉淀是默认开还是默认关**：沉淀要存工作区输入快照与完整轨迹，占磁盘、也是隐私面。
   建议**默认开但只在项目内**，并在设置页给「查看/删除我的 episode 池」——
   用户必须能看见自己被记录了什么。
7. **题族的失败模式打标由谁做**：规则匹配（便宜、可解释、覆盖窄）还是模型打标（覆盖宽、要花钱、会漂）？
   建议 M0 用**用户便签的文本本身作为 key + 模型做召回**，先跑起来再谈自动发现新模式。
8. **导入数据集学到的东西能不能自动转正**：护栏 2 说必须过真实 episode 回归，
   但新用户可能长期没有真实 episode。是"永远停在试用版"，还是给一个
   「我确认接受，直接转正」的手动逃生门？建议**给逃生门但要用户显式点**，
   并在版本时间线上永久标注"未经真实回归验证"。
