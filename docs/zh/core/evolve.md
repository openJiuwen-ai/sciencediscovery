# 程序演进（`/evolve-design`）

`/evolve-design` 靠反复搜索而不是一次修改来把东西做得更好。你把"更好"定义成一个数，产品写出几十个变体、逐个打分、留下分更高的，最后把最优版本和起点一起交回来。

> 本文说明搜索是什么、什么时候有效、为什么这样设计。要跑一次见[运行一次演进搜索](../domains/run-an-evolution-search.md)；要一个能完整跑完的第一次搜索见[教程](../domains/evolve-a-solution.md)。引擎内部与侧车独立部署见[演进侧车：架构、引擎与独立部署](../developer-docs/evolve-standalone.md)。

## 搜索到底是什么

候选可以是任何文本形态的东西：一个函数、一整个程序、一段提示词、报告的一节、一个配置文件、一份实验方案。一次迭代选一个父节点，让模型把它重写一遍，用你的评分方案跑一次结果，记下分数。在预算内重复。

所以一切都压在一个性质上：**评分必须能把好候选和坏候选分开。** 分不开不会报错 —— 它表现为一条平掉的曲线，二十次扩展全落在同一个数上，预算花完而没有任何信号。下面的设计有大半是为了在它花掉你一次运行之前就把这种情况拦住。

![在输入框里一句话发起搜索](../../images/evolve/start-a-search.png)

发起方式就是在会话里说清楚你要什么 —— "写一对 compress/decompress，无损前提下压缩比越高越好"。`evolve-design` 技能通过四个检查点把它变成一份搜索方案，服务端负责执行。

## 四种打分方式

打分模式是让同一套搜索引擎服务于差异极大的目标的接缝。四种对两个引擎都可用。

| 模式 | 分数来自 | 适合 |
|---|---|---|
| `dataset_metric` | 在带标注数据上算出的指标 | 预测、拟合，任何"有张表、有一列要算准"的任务 |
| `test_gate` | 测试套件的通过率 | 正确性由测试定义而不是由某个数定义的代码 |
| `custom_script` | 由起草模型自己写的评分脚本 | 既没有表也没有测试套件的确定性目标 —— "把这些地址切成四个字段，越准越好" |
| `llm_judge` | 裁判模型对照冻结的评分细则打分 | 散文、提示词、方案、计划 —— 没有东西可执行也没有东西可测量的场景 |

`llm_judge` 是 `/evolve-design` 能作用于"不是跑在表上的程序"的原因。它也是唯一**非确定性**的模式，所以细则要冻结，而且它的运行比其他模式需要更大的单元。

## 两个引擎

两个引擎共用同一套 Domain 接缝 —— 起点程序、候选怎么打分、重写候选的提示词、被报告的那个数叫什么 —— 只替换算法核心。

![发起搜索时在 PUCT 与 OpenEvolve 之间选择](../../images/evolve/choose-algorithm.png)

**PUCT**（`puct`）维护一棵树。每个候选是一个有父节点的节点，树是追加式的，选择规则是 `rank + c_puct · P · √总访问数 / (1 + 访问数)`。适合在一个起点上持续精炼。

**OpenEvolve**（`openevolve`）维护多岛 MAP-Elites 归档：`岛数 × feature_bins²` 个格子，按代码复杂度与代码多样性分箱，一格一席；每 `migration_interval` 代，各岛最优通过环形迁移复制到下一个岛。父选择用 ε-greedy（70% 选最优，30% 随机），变异提示词里还会带一个与父代码差异最大的 **inspiration** 程序。适合解空间宽、树搜索容易早熟收敛的任务。

选择在提交搜索方案时给出；不选就按 PUCT 跑。

## 为什么最后报告的那个数可信

### 数据三分

| 分片 | 谁能看见 | 决定什么 |
|---|---|---|
| `rollout` | 搜索 | 搜索自身的走向 |
| `gate` | 搜索 | 每个候选的排名 —— 树据以选择的那个数 |
| `test` | 结束前谁都看不见 | 报告给你的数 |

任何参与引导搜索的环节都不碰 `test` 分片，所以最后给你看的数不可能被搜索过程本身抬高。这也是 `gate` 应当是三者中最大的原因：它是搜索唯一真正据以转向的数，gate 太小意味着整场运行里树都在对噪声排名，而且是静默的。

### 开跑前先验证判别力

在花掉预算之前，服务端先用四次沙箱评测检查评分方案是否真的能区分：能不能把正常程序和被故意弄坏的程序分开、起点是否还有提升空间、重复评测是否稳定、失败诊断是否带足够的定位信息以便修复。过不了这一关的方案会被拒绝并说明原因 —— 在它花掉你一次运行之前。

### 评分器是冻结的

候选不能修改衡量它的东西。这条规则分两层强制 —— 提示词里声明的冻结路径过滤器，以及其下的执行层 —— 理由上游说得很直白：*没有它，拿高分的最短路径就是把衡量它的那把尺子改弱。*

## 它在哪里执行

搜索在独立侧车进程（`services/evolve`）中执行，每个候选都在与产品其余代码相同的 bubblewrap 沙箱里评测。侧车的模型调用使用 run 级临时 token，服务商密钥不出控制面。侧车唯一的客户端是 Node 控制 API。

跑不起来的候选会带着自身报错获得有限次数的自动修复；修复后的候选只有在分数严格提高时才被采纳。

## 一次搜索的代价，以及什么时候不该跑

每次扩展是一次模型调用，加上对搜索可见分片中每个单元的一次沙箱评测。所以预算按扩展次数计，合理区间取决于搜索要走多远：已知缺陷 4–6 次，换思路或重构 12–20 次，从零写 20 次以上。

已经知道该怎么改的时候不该用搜索 —— 那是一次修改，不是五十次。没有任何数能区分好坏的时候也不该用："结构清晰、可读性好"对任何文档都成立，只会跑出一条平线。

最后，一次没能跑出高于起点的运行**本身就是结果**：在这套评分下，这些变体赢不了起点。此时正当地属于你去重新考虑的是**评分** —— 那些用例是否真的奖励了你在意的东西、语料是否宽到足以区分不同思路 —— 而不是你希望候选采取的那条路子。
