# 科研 Agent：从问题到可检查的研究过程

ScienceDiscovery 的核心不是一次问答，而是让 Agent 围绕一个研究目标持续工作：理解问题、选择方法和工具、执行具体步骤、检查中间结果，并把有价值的结果交付为可以继续使用的科研产物。

你可以只提出目标，不必预先把每一步都写成固定流程。Agent 会根据当前任务、可用工具、Skill、Specialist 和已有材料决定下一步行动；重要操作仍受权限与运行环境约束。

## 主 Agent 负责把研究目标串起来

一个 Session 中的主 Agent 持有当前任务目标和上下文。它可以：

- 阅读你提供的文件和消息；
- 使用可用的 MCP 工具获取外部数据；
- 按需要加载 Skill 作为工作方法；
- 在科研执行环境中运行代码；
- 把适合独立处理的工作交给 Specialist / 子 Agent；
- 汇总结果并生成 Artifact。

因此，ScienceDiscovery 的工作流并不要求你先手工选择所有能力。你可以从研究问题开始，再通过执行记录检查 Agent 实际使用了什么。

## 子 Agent 用于分工，不代表结论更可靠

复杂任务可以被拆成多个相对独立的子任务。例如一项文献调研可以分别检索不同证据方向，一项数据研究也可以把代码实现与结果复核分开。

子 Agent 的价值在于：

- 将不同任务上下文分开；
- 允许并行推进部分工作；
- 让职责和交付更清楚。

但“多个 Agent 得到相似答案”并不等于独立科学验证。多个角色可能共享同一个模型、相同资料或相似偏差。最终结论仍需要来源、计算和实验依据支持。

## Agent 可以调用什么，由当前 Session 决定

Agent 能看到的能力来自当前运行环境和 Session 配置。常见组成包括：

| 能力 | 解决的问题 |
| --- | --- |
| MCP | Agent 能访问哪些外部工具、数据库和服务 |
| Skill | Agent 可以采用哪些可复用研究方法 |
| Specialist | 哪类角色负责某种工作，以及它可使用哪些方法和工具 |
| 科研执行环境 | Agent 在哪里运行 Python、R 和 Shell |
| Artifact | 哪些结果被正式交付、版本化并供后续复核 |

可以把它们简单理解为：**MCP 是工具，Skill 是方法，Specialist 是角色，Artifact 是交付物。**

这些配置决定 Agent“可以怎么做”，并不保证模型每次都会调用某个能力。实际行为应以时间线、工具调用和最终产物为准。

## 一次典型研究如何推进

例如，你提出：

> 调研一种疾病的主要分型方法，比较证据，并对一份本地患者数据做初步分析。

Agent 可能形成这样的过程：

1. 明确问题范围和需要的证据；
2. 调用文献相关 MCP 检索来源；
3. 使用文献研究 Skill 整理证据；
4. 将部分检索或证据提取交给 Specialist；
5. 在科研执行环境中运行数据分析代码；
6. 比较文献证据与计算结果；
7. 生成报告、表格或脚本等 Artifact；
8. 如启用 Reviewer / ScienceMemory，再对产物进行检查和追溯。

这不是固定编排。任务不同，Agent 可以采用不同策略；你应检查过程和产物，而不是假设某一步一定发生。

## 用户仍然掌握研究方向

Agent 可以减少重复操作，但不替代研究者对目标、证据和方法的判断。尤其在以下情况，应主动介入：

- 研究问题本身含糊；
- 数据或来源的边界不清楚；
- Agent 需要高影响权限；
- 中间结果偏离研究目标；
- 关键结论缺少可核查依据。

ScienceDiscovery 的目标是把更多研究步骤变成可以执行和检查的过程，而不是让“自主”代替科学判断。
