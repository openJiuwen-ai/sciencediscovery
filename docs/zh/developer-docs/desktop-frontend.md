# 前端：`apps/desktop`

`apps/desktop` 是同一 workspace 内的第二个 React 工作台，按 v0.1 设计稿实现，目标是替换 `apps/web`，也是 Electron 外壳加载的前端。在 `SCIENCE_AGENT_WEB_DIR` 改指之前，根路径仍由 `apps/web` 提供；两个前端共用同一个控制 API 和同一个 token key，因此切换时不需要二次登录。

## 1. 技术栈与和 `apps/web` 的关系

- React 19、Vite、`@vitejs/plugin-react`、原生 CSS；没有 router、状态库和 UI kit，约束与 `apps/web` 相同。
- Markdown 只经由 `react-markdown` 与 `remark-gfm` 渲染。
- 类型来自 `@sciencediscovery/schema`，由 `src/api/types.ts` 用 `import type` 再导出。这个再导出把 schema 的 barrel 挡在浏览器 bundle 之外；在那里加一个值导入会把整个 catalog 拉进 `dist`。
- `apps/desktop` 不依赖任何 service，也不依赖其他 app。架构检查把 `apps/*` 视为 host，所以这个方向是允许的，而 package 永远不能反向依赖它。

## 3. 与服务端通信

请求统一走 `ApiClient`：注入 `authorization: Bearer <token>`，非 2xx 转成携带服务端 `error`、`code`、`details` 的 `ApiRequestError`。`PUT /api/settings` 是整对象写入，所以 `setGlobalModel()` 总是先读、再把已有 override 原样回传、只改一个字段；省略的字段会被 `store.replaceGlobalSettings` 抹掉。

流式响应使用 `fetch` 加 `body.getReader()`，不用 `EventSource`，因为 token 必须走 header。`SseFrameDecoder` 以空行分帧、忽略 `:` 保活、并缓存尚未收到结束符的半帧——chunk 边界可能落在任何位置，包括 `\r` 与 `\n` 之间。帧携带 `id: <n>`，即 `?after=` 的续传游标；重连时从已见的最大值继续，而不是重放整个 run。

两个流入口含义不同：

| 调用 | 含义 |
|---|---|
| `POST /api/sessions/:id/messages` | 发送一条消息并流式返回它启动的 run；服务端在终态关闭响应，所以响应体结束即 run 结束 |
| `GET /api/sessions/:id/runs/:runId/events?after=N` | 以 SSE 跟随一个已存在的 run；同一个 URL 按 JSON 读就是已结束 run 的重放，重建时间线走的是这一条，因为它自己会结束，而不是一条需要主动关闭的流 |

客户端断开不会取消任何东西。只有 `POST /api/sessions/:id/runs/(:runId|current)/cancel` 能停止 run，因此输入区的停止按钮是离开正在运行的回合的唯一出口。也正因如此，允许在 run 运行中离开 Session：run 在服务端继续，再次打开该 Session 会重放它并接着跟随还活着的那条。运行中切走是用户继续处理其他事情的方式，所以侧栏和新建会话按钮都不会因此禁用。

新增会话按钮在**点击时**就用 `POST /api/projects/:id/sessions` 创建 Session，而不是等第一条消息。侧栏列的是服务端已有的 Session，一个只存在于界面里的草稿会让按钮看起来失效，也会让第一条消息像是凭空多创建了一个 Session；先创建意味着点击、侧栏和输入区从第一秒起说的就是同一个 Session。没有打开 Session 时发送第一条消息走同一条创建路径，所以两个入口只产生一个 Session；创建请求在途时重复点击会复用同一个请求。启动时，第一次列出会话之后应用会打开最近使用的那一个——和点击那一行打开的是同一个会话；否则启动后的界面是一个草稿，侧栏里却已经列着会话，第一条消息会紧挨着它再建一个。要开新会话，点「新增会话」。删掉当前打开的会话则回到无会话的草稿态，下一次写入（消息或上传）再新建——删除之后自行补一个空 Session 不是这个应用该做的决定。

最近列表保留全部 Session，而不是停在某个固定条数：它占用侧栏剩余高度，超出后自行滚动，滚动条在列表右缘，品牌区、新增会话和设置入口保持不动——隐藏一个仍然存在的 Session，读起来就像它被删了。列表只在一个方向滚动：`overflow-y: auto` 会把另一轴也算成 `auto`，一行稍宽就会在底部出现横向滚动条；因此 `overflow-x` 设为 `hidden`，滚动条本身是一条 8 px 的细轨道。

## 4. 事件到 UI 的映射

| 事件 | UI |
|---|---|
| `run.queued`、`run.started` | run id 与模型名；启动 run 的 `POST` 不返回 id，所以在这里取得 |
| `assistant.thinking.delta`、`assistant.thinking.snapshot` | 折叠的「思考过程」块；snapshot 替换、delta 追加，截断的 snapshot 不会让屏幕上已有的内容变短 |
| `assistant.response.started`、`assistant.delta`、`assistant.snapshot` | 每次模型调用一个正文块，所以被工具调用打断的回合会渲染成两段 |
| `assistant.response.settled` | 正文块停止显示 spinner |
| `run.status` | 终态判断，使用与服务端关闭响应时相同的状态集合；它带的那个 run 同时带来 `startedAt` 与 `finishedAt`，折叠行的「用时」就取自这两者 |
| `run.completed` | 已持久化的消息优先于拼装的 delta；流式块被封口 |
| `run.failed`、`run.cancelled` | 失败码与取消原因显示在 run 状态行 |
| `run.history.truncated` | 提示更早的事件无法重放 |
| `tool.started`、`tool.completed` | 「工具调用」卡片，按调用发生时所在的回答下标插进回答块之间 |
| `permission.required`、`permission.resolved` | 带三个按钮的「需要权限」卡片，按 `request.id` 归并，因此重发来的快照不会把决定撤销掉 |
| `artifact.*`、`plan.*`、`subagent.*`、`agent.*`、`session.updated` | 有意延后；单独计数，不计入「未知事件」 |

有两个事件需要表格之外的解释。工具调用是**落位**的而不是罗列的：`AssistantTool` 记下 `after`，即它所跟随的那条 `responses` 的下标，`-1` 表示「在第一条回答之前」。方向要看准：`after === i` 是排在第 i 条回答**之后**，因为这个值是在 `tool.started` 到达时按 `responses.length - 1` 记下的，而那一刻模型刚刚说完第 i 条；把它当成「插在第 i 条之前」会让工具卡跑在它所解释的那句话前面。这正是 agent 循环的形状：模型说一段话、调一次工具、再被重新调用。`tool.completed` 不重复携带参数，所以 reducer 从 start 事件把它们带过来；更早的记录若仍然重复携带，则以完成事件里那份为准。

对话是两个人的两侧：读者自己的回合在右侧，头像是一个默认的灰色人形剪影——用形状而不是过去代表读者的字，因为那个字读起来像角色徽标；模型回答在左侧，配模型名的首字母。用户回合的正文在 DOM 中位于头像**之前**，网格把它放在右列、头像在外缘，这样读屏软件和窄窗口都会先遇到正文再遇到装饰。气泡按内容收缩，最宽 560 px，而不是铺满整列。

一次 run 在提问与回答之间做的所有事情都折进一行，而且这一行从 run 一开始就是折叠着的、不是等结束才折：一次上百轮的 run 只占 transcript 的一行而不是上百行，而且它在 run 工作的整个过程中都在，而不是停下之后才出现。刚发出的消息靠那条待发消息来渲染它，但要晚一秒才画，而不是跟按下发送挤在同一帧——占位行跟按键同时出现，看起来像一段写死的动画，而不是收到了消息；而流里真正产出东西时则立刻画出来。运行时那行标题写「正在思考」，旁边是一圈转动的圆环，这也是 transcript 里唯一会动的图标，于是这行不用让人去信一个静止的字形就知道正在干活；run 在等待而不是在工作时写「排队中」或「等待授权」，图标保持静止，因为等待不等于工作。结束后写「用时 12 分 3 秒」，取自 run 带来的 `startedAt` 与 `finishedAt`，圆环也随之消失。这两个时间还不存在时记下的老 run 没有可度量的跨度，退回显示它的状态词。流式指示属于**某个 response**，而不是整个 turn：只有 `settled` 仍为 false 的那个 response 在转。用「是不是这个 turn 的最后一个 response」判断会给每个 turn 都画上转圈，因为每个 turn 都有自己的最后一个 response。

有两样东西刻意留在折叠之外。一是回答：整个 run 里**最后一条有正文的** response，于是模型可以被重新调用十几次，用户看到的一直是他在等的那句话边生成边长（带转圈）；而且在 run 还在跑时它必须属于**最新那一轮**，否则那句引出工具调用的话会在整个工具执行期间被当成结果显示，之后再被收进折叠里。二是未答复的授权卡，那是一句问**读者**的话：把提问折进收起的一行里，会让这次 run 看起来毫无来由地停住了。普通的一问一答中间什么都没有，因此一行也不出；同理，一个什么都没留下的 run（开了轮次却没吐出任何正文，比如网关直接拒了）连角色名那行也不出——只有状态条，否则屏幕上会多出一个顶着第二个头像、底下一片空白的模型名。

工具的输出根本不在 run state 里。它写进自己的子流 `tool-<toolCallId>`，卡片在第一次展开时读一次 `GET /api/sessions/:id/runs/:runId/streams/:streamId/events`——这是几个读取入口里唯一的 JSON 路由，因为它读的是另一条流。用 `?after=0` 重放的 run 里**完全没有** `tool.output`，只有指向子流的 `tool.completed` trace，所以指针必须由 trace 携带。直播响应确实会把那些帧扇出来，而它们不带 `id:` 行；它们被单独放进一个集合丢弃，既不计数为未知事件，也不推进重放游标。

思考过程没有持久化形式：`ChatMessage` 只带最终文本。因此打开会话时会重放它的 run，并把每一条重建放回**它自己那条**回答的位置；当重放没有产生可见内容时回退到已存储消息——这正是「重连后什么都没拿到」不会渲染出空白回答的原因。

被重放的是**每一次已终结的 run**，不只是最近那一次，而且每次 run 各占一份 state：reducer 用事件自带的 `turn` 号做 key，而这些编号在每个 run 里都从 1 重新开始，把两次 run 折进同一份 state 会让第二次 run 的第 1 轮悄悄并进第一次的。一个跑过好几轮的会话因此每次 run 一份重建——被自动唤醒打断的那一次，会在「唤醒」通知的另一侧带着自己的思考与工具调用重现，而不是只留下一句没有来历的回答。轮次编号来自服务端、每个 run 各自从 1 开始，所以同一段 transcript 的两节可能都从「第 1 轮」起；这里不做重新编号，因为连续编号会打印出服务端从未给过的数字。

落位按消息走：一条重建会顶替它那次 run 写下的回答，而没写过回答的 run（比如先被取消）跟在开启它的那条消息之后。两处都对不上的 run 才会落到 transcript 末尾。还在直播的 run 还没有持久化回答，所以它一直排在最后，直到下一次 `settle` 重新读取会话、把它和其余的一起折进去。

自动唤醒本身不再绘制卡片。唤醒没有用户撰写的正文——schema 有意把面向模型的 prompt 排除在 `content` 之外，正是为了不让唤醒被当成用户输入——所以它的卡片曾是一条带头像的空白条，说不出任何下面那个 run 没说清楚的事。但那条消息仍留在 `messages` 里：唤醒所启动的那次 run 正锚在它这里，删掉它会把那次 run 送到 transcript 末尾，而不是送到事情发生的位置。

对一次重放要问两个问题，而它们并不相同。第一个是值不值得留下：没有任何持久化事件的 run 会折成一个空 state，留下它等于在 transcript 里挂一段空白的回合。第二个是能不能顶替已存储的回答：只有写出回答的 run 才能，所以在开口之前就失败或被取消的 run 保留它的状态行——那是它全部的下落说明——而已存储的消息留在原地。混淆这两者，正是让一次失败的 run 在界面上不留任何痕迹的原因。

右侧面板是页签式的，不是分区式的。它打开时是一个标题为「新标签页」的页签，内容是产物分区与工作区文件树；打开的第一个文档会就地替换这个页签的内容——它是唯一会被覆盖的页签，所以「只看一个产物」不会多出一个页签。在已经显示文档时再打开文档会新开一个页签，这也是从预览里点链接不会破坏原内容的原因。关掉最后一个页签等于收起面板，同时留下一个全新的初始页签：既不留空页签，也不存在零页签的面板。离开会话会丢弃它打开的文档，因为这些文档属于那个会话的工作区。

面板宽度可以拖：下限 280 px——再窄文件树上的名字、大小与时间就排不进一行；上限 720 px——再宽这个侧栏已经变成主栏，被它挤压的正是它本来要评论的那段对话。宽度出现的那两处由同一个值驱动：`App` 把 `--panel-width` 设在 `.app-shell` 上，栅格第三轨是 `var(--panel-width)`，面板自己的宽度读同一个变量，所以列与填进列里的东西不可能对不上。**记住的宽度**与**渲染的宽度**刻意是两个数：用户要的那个写进 `localStorage`（只按面板自身的上下界夹取），渲染的那个是它再按当前窗口能给多少折一次——要给对话列留出最小宽度。反过来把记住的值也夹掉，窄窗口就成了破坏性的：天花板会被写下来顶替宽度本身，等窗口再拉宽，面板会一直窄成它待过的最小的那个窗口。拖拽跑在分割条自己被捕获的指针事件上——指针立刻就会离开分割条那六个像素（面板是从光标底下长出来的），捕获让事件继续送来；也只有拖拽停下的那个宽度会落盘，因为每一次 pointermove 都序列化一次会变成整个拖拽里唯一可能卡顿的一环。

产物分区每行只有一个名字和一个小圆点。名字是**文件名**而不是产物名本身：产物名是 `antibody_pipeline/runs/<run>/…` 这样的相对路径，一趟运行的每一行都带同一串目录，在这么窄的一列里只会把各自不同的那一段挤出去（`app/paths.ts` 的 `fileName`）。完整路径留在 tooltip 里，打开后在标题下那行 `<small>` 里再出现一次。服务端给每个产物带的 `description` 是一整段说明，一行一段说明的列表会把「选哪一个」所依赖的名字淹掉，所以名字之外的内容都不再渲染；那段说明仍然作为行的 tooltip 保留（没有 `description` 时 tooltip 回退到完整路径），内容本身点一下就在页签里打开。圆点的颜色就是产物的 `kind`，替代了原来那行「类型 · vN」文字。

工作区文件树是**一层一行**：`antibody_pipeline/runs/<run>/…` 折成一棵真的树，`antibody_pipeline` 一行、`runs` 是它下面的一行，而不是把整条路径按斜杠写成一个名字。折树的是纯函数 `app/file-tree.ts`——不碰 DOM，所以可以直接单测：按 `/` 切段，每段一个节点，同一个路径的目录共用同一个节点，于是同一个目录不可能现身两次（按整条路径分组时，`runs` 会在每个 `<run>` 底下各印一行）。每一层目录排在文件前面，各自按名字排序；文件显示的是**文件名**（同产物分区那条理由），完整路径留在 tooltip 里。目录行右边那个数字是它**下面全部**文件的数量，一路递归到底，所以不展开也知道里面有多少东西；展开与收起用 `<details open>`，默认就是展开的，打开面板第一眼看到的仍是完整列表，只是名字短了、层次清了。缩进是要花宽度的，面板拖到 280 px 时一条四层的路径已经把它花完，所以右边的列一层层让出去：先舍大小（目录行本来就没有大小，而三层深的一个文件是来看名字的），再舍时间（父级的计数和产物分区都会再说一遍），剩下缩进和名字——那正是画一棵树的全部理由。

结构浏览器就是这个面板里的一种预览，不是另一种窗口。分子与晶体结构（`pdb`、`ent`、`pqr`、`cif`、`mcif`、`mmcif`、`mol`、`sdf`、`mol2`、`xyz`）打开时由 Mol* 就地渲染在文档页签里，其余文档仍按原来那样走 markdown、JSON 与源码预览。之所以不弹窗，是因为它就同别的产物一样是一份文档：页签规则已经回答了「打开第二个会不会盖掉第一个」，再为它单开一种呈现方式只会让同一份文件有两条到达路径，而这两条路径迟早会不一致。

是否把它交给 Mol* 由 `src/molecular.ts` 判断，顺序是先看文件名后缀、再看媒体类型、最后嗅探内容。后缀为 `.json` 的一律不交给 Mol*：Mol* 根本不读 JSON，而这个平台唯一叫「结构」的 JSON 是自己的 `.structure.json` 原子列表，它应该按文档预览。`.cif` 还要再分一次——带 `_atom_site.Cartn_x` 的走 mmCIF 解析器，只有 `_atom_site_fract_x` 与晶胞参数的走 CIF core；把后者喂给 mmCIF 解析器会得到零个模型，界面显示「No models found」而不是结构，所以两者不能共用一个格式。晶体结构另外先按对称性展开成晶胞（`unitcell` 预设），因为通用预设只画不对称单位、还隐去晶胞框——对岩盐那就是两个原子；文件里没有可用对称性、预设拒绝时再退回通用预设并显式画出晶胞框。

Mol* 自己的面板是按整个窗口设计的，而这里是一个侧栏里的文档页签，默认 360 px 宽，所以插件以「区域全部隐藏」的方式挂载；它另外画在画布上的两条控件——左上角的动画选择、右侧的视口按钮条——也一并隐藏：这两条里没有一个是关于这个盒子的，这个盒子自己的入口就是点一下模型。把面板拖宽不是把它们请回来的理由——到了 720 px，问题变成 Mol* 那些面板到底是不是关于这个盒子的，而答案仍然是不是。点模型，或者点它上面的文档名，会把同一个视图放大到全屏——还是同一招，这个盒子逃出栏目；画布不重新挂载，所以转到什么角度，放大之后还是那个角度，Esc 与右上角的 ✕ 都能退出。

Mol* 的面板随全屏一起回来。为它重建插件是另一回事——那意味着第二个 WebGL 上下文、同一份文件再解析一遍——所以这里改的是正在运行的那个插件的布局，走 `PluginCommands.Layout.Update`。这是唯一既合并状态、又发出 `layout.events.updated` 的路径，而插件自己的布局组件正是订阅这个事件才重绘的；四个区域是按 `showControls` 条件渲染的，所以用 `plugin.layout.setProps()` 赋个值只会让面板依旧不挂载、且没人被通知。唯一刻意不碰的是 `isExpanded`：Mol* 把那个标记当作它自己的全屏模式，会去改写 `document.body.style`、把 viewport meta 搬进它自己的容器，而这里的全屏是本应用自己的覆盖层——下面那一页必须留在原地。布局改完之后会重新让插件量一次尺寸，因为面板占走的宽度画布已经没有了；两个方向都必要，因为「从一份文档里的链接打开另一份文档」时，插件是被挂载进一个已经展开的页签里的。盒子的尺寸还有第三种变法，由挂在盒子上的 `ResizeObserver` 兜住：拖动面板会让盒子变宽变窄而**没有任何 state 变化**，组件里别的代码就都不会运行，模型会一直停留在它第一次画出来时的尺寸。观察器会忽略尺寸为零的盒子——被隐藏的面板就是零尺寸，而把一个 WebGL 画布量到零再量回来，就是上下文丢失的常见来路——重量的同时还要重绘，因为只改尺寸不重绘会让新露出的区域空着，直到下一次指针事件，而看一张静止的图时这可能很久。全屏态还把悬浮的名字与徽标换成了真正的头部条，因为那两个角现在归 Mol* 的面板了。渲染交给 Mol* 的自适应预设——聚合物用卡通、配体用球棍、晶体画对称展开的晶胞——这是在任何人做出选择之前唯一不撒谎的答案，也是唯一不必选的默认。徽标只写两件事：这个文件的格式，以及插件状态里数出来的原子数——没有数字来源的地方就不写数字。

Mol* 及其依赖约 3.2 MB，因此这个视图是一个动态 import 的独立 chunk：只有真的打开结构文件时才会去取它，主包不受影响。也因此它无法在本仓库的测试环境里渲染——那里没有浏览器与 WebGL——所以能被测的部分被刻意留在外面：格式判断在 `src/molecular.ts`，以及面板里「标题是不是那个按钮」这一步（静态渲染的面板只走到 Suspense 兜底，不引入 Mol*）。

## 5. 首次运行与设置

`GET /api/models` 返回空列表就是首次运行条件，因为没有模型就发不出消息。向导随后直接进入提供方配置，模型一步必须通过 `POST /api/models/:id/test` 之后主界面才可达。工作区与本地服务已经由外壳在加载这个前端之前处理完毕，所以这里是单步页面，不再重复工作区与启动页。

下面的顺序由 API 决定，不是偏好：`PUT /api/settings` 会按当前模型目录归一化，并丢弃指向不存在 profile 的 `modelId`。

1. `POST /api/providers`——若该 base URL 已有提供方则改为 `PUT /api/providers/:id`，这样改对密钥不会留下重复记录。
2. `POST /api/providers/:id/models`——只有 `{model}` 是必填；手填的模型名与探测到的走同一条路径。
3. `POST /api/models/:id/test`。
4. 合并覆盖项后 `PUT /api/settings`。

「拉取模型清单」使用 `POST /api/providers/preview-models`：它用表单里的地址与密钥去拉取，不持久化任何东西——`GET /api/providers/:id/models` 会要求先保存一份半填的提供方。拉不到清单是常见情况，模型名随时可以手填。

预设会带上 `apiProtocol` 与 `apiVariant`；只有自定义分支才询问协议，因为地址正确但 variant 选错的表现是「密钥坏了」。

设置 › 模型 只剩两块：已配置的模型（每张卡片带「测试」与「设为默认」，当前默认用标签标出），以及添加模型表单。默认模型不再是页面顶部单独的一块——它只出现在卡片上。表单里每个字段下面都不再有一句说明，也没有「还没测试…」那句话；底部并排三个按钮，各做各的事。「测试」会先把这份配置写进目录，再调 `POST /api/models/:id/test` 报告结果——连通测试只认已经存在的 profile，而同一提供方、同一模型名重复写入在服务端是幂等的，所以先测再存不会留下重复记录；它不改默认，也不关闭表单。「保存」走完整链路：写入、测试、设为默认，通过之后才关闭。「取消」只关闭表单，不再写设置（向导没有取消按钮；模型配置不通过就不进入主界面）。

数据目录由外壳在启动前选择，桌面端不再重复询问：没有任何路由能返回或修改运行中的数据目录，它来自服务启动参数。

设置弹窗是三个分组下的五个页面——「通用」属「系统」，模型、技能属「智能」，网络、远程属「连接」，不再单列「工作区」组；除「通用」外每页挂载时自己读数据（`src/app/use-loaded.ts`）。「通用」是浏览器自己的页面，不是服务的：它唯一一行是界面语言（简体中文或 English），选中即生效，存在 `sciencediscovery-desktop:locale` 下，和 `apps/web` 的即时切换一致。默认是中文而不是浏览器偏好：这个界面面向中文优先的部署，否则英文浏览器会直接以英文打开，还不告诉用户有这个设置。`TEXT` 不再有任何模块级读取：它是套在当前词典上的代理，App 订阅语言存储，一次切换就重渲染整棵树；原先写在组件里的字面量与模块级标签表（通知种类、沙箱模式、run 状态词、工作区的相对时间、「未命名会话」「你」「第 N 轮」）现在都是词典条目；连折叠行那句「展开/收起」也一样——它由 CSS 依据 `details[open]` 打印，译文装在 `data-expand`/`data-collapse` 属性里，而不是写死在 `content` 中。`<html lang>` 跟着选择走，首帧之前设置一次，之后每次切换再设置。每个小节标题都独自成立：以前每个标题下面还会有一句话解释这一块是干什么的，现在都删掉了——标题就是介绍。读取失败时渲染失败原因和一个重试按钮，而不是一个空列表：在设置页上，空列表是对服务端状态的断言，请求失败时它就不是真的。

写操作落在哪一层并不统一，而且从界面上看不出区别：

| 设置项 | 路由 | 为什么是这条 |
|---|---|---|
| 默认模型、沙箱网络 | `PUT /api/settings` 或各自的专用路由 | 全局设置，且整体替换写必须先读、合并、再发回 |
| 技能 | `PUT /api/projects/:id/settings` | 全局层会跳过技能字段，写过去会被静默丢弃；同时必须在同一次请求里把 `skillSelectionMode` 钉成 `selected`，否则 `all` 会在下次读取时把白名单重新展开 |
| 远端机器的登记、登录凭据、主机密钥 | `POST /api/remote-hosts`、`PUT /api/remote-hosts/:id/credentials`、`POST /api/remote-hosts/:id/trust-host-key` | 凭据只进不出，写入后的响应本身就是一次新探测的结果；接受主机密钥是独立的一步，不能混在别的一次写里 |
| 项目可用的执行机器 | `PATCH /api/projects/:id`（`runnerIds`） | 这是 Project 自身的字段，而且必须整份发回——它是一条完整名单，不是增量 |

对话框里模型按钮与回形针之间原本还有一颗「会话配置」，它唯一的行是权限模式。这颗按钮连同会话级的 `approvalMode` 写入一起拿掉了——路由还在，但这个应用不再发它。还依赖权限模式的只有运行本身：会话建立时的模式留在服务端，需要授权的回合仍然会停下来，用授权卡发问。

面板里不出现的东西，是从界面上按需求删掉的，不是能力不存在：设置里不再有专家、连接器、权限、反馈四页；「通用」只剩界面语言（它原先展示的那个仅作记录的数据目录已经不存在，不是设置项）；网络里只剩沙箱网络：「无网络」「域名白名单」「开放网络」三档，白名单模式带着一个域名输入框和它自己的「保存」按钮——服务端不接受空名单，而输入框在别的模式下是禁用的灰色，所以选白名单只切换编辑状态，模式与域名在按下「保存」时一起写入；「无网络」与「开放网络」仍然点哪档就立刻写哪档，只有切到「开放网络」时仍会先问一次；允许内网与回环地址、白名单流量的出站路由、以及那句保存警告仍不在界面上，代理服务器的清单在这里也不再读；远程里只剩 Runner，卡片上不再有「测试连接」按钮（连接、信任主机密钥、保存凭据仍然会探测）；对话框里不再有「会话配置」；会话也不再从这个应用归档或取消归档，侧栏行菜单只剩重命名与删除。会话栏也不再挂 ⋯ 菜单（改名走双击标题，或侧栏行的菜单）。

### 远程页的执行机器

`GET /api/runners` 返回的是本机加全部远端机器。本机那一条是服务端造出来的（id 恒为 `local`）：它永远存在，也不能删掉或改地址，所以远程页的机器卡片里不列出它——这一页管的是别的机器，而给「应用自己正在跑的那台机器」留一张卡片，会让这页上的每一个操作都不适用于那一行。它仍留在下方的可用机器名单里：「这个项目能不能在这台机器上跑」是个真问题，本机是一个有效答案。留下来的每一张卡片背后都有一份远端机器记录。两种远端类型走的是两条不同的路：`ssh` 由本机代持一条 SSH 连接并把 Runner 部署过去，`direct` 直连一个已经在别处跑起来的 Runner，只要地址和访问令牌。

登记一台 SSH 机器时，主机密钥是绕不过去的一步，而且它不是一个错误。第一次连接会以 409 返回 `SSH_HOST_KEY_UNTRUSTED`，如果这台机器此前已被信任、现在出示的却是另一把钥匙，则是 `SSH_HOST_KEY_CHANGED`；两者都带 `details.hostKey`（算法与指纹）与 `details.hostId`。界面上它呈现为一个问题，指纹以 `ssh-ed25519 · SHA256:…` 的形式原样列出——这正是 OpenSSH 自己打印、用户拿去比对的那一行——接受之后才重放刚才失败的那次操作。没有指纹就不问，因为让人接受一把不告诉他是哪把的钥匙，等于要一个盲目的「是」。探测失败但拿到了密钥时，服务端会把已登记的机器连同 `hostKey.trusted === false` 一起返回：这仍然是一个问题，界面按同一个卡片处理，而不是当成保存失败。

登录凭据是只写的：`PUT /api/remote-hosts/:id/credentials` 里出现的字段才会被覆盖，缺席表示保持原值，`null` 表示清除。因此凭据表单打开时每个框都是空的，占位文字写的是「保持已存的那一个」，而「这台机器已经存了密码／私钥」这件事由机器卡片以标签形式陈述——读不回来的值不能假装读回来。私钥是以路径给出的，因为要读它的是 API 所在的那台机器；如果私钥在用户自己手上，就在表单里现生成一对，面板只显示公钥那一半，并说明它要装到哪台机器上。

连接与断开是两条语义不同的路：`POST /api/runners/:id/disconnect` 总是成功，而 `connect` 只在就绪时返回 200，否则以 503 返回失败状态本身。也就是说，连接失败时拿不到一句「为什么」，原因写在连接日志里：界面在连接进行中以 800 ms 轮询 `GET /api/runners/:id/connect-log` 并把日志行铺在卡片下方，失败后再多取一次，让最后几行停在屏幕上说出原因；成功则清空。日志行是给运维看的诊断文本，不是界面的措辞，所以原样显示。

连上的机器会汇报自己有什么。`runnerStatus.resources` 带工作区磁盘、内存、CPU 核数、1 分钟负载、运行时长和采样时间，机器卡片把这些收在「机器详情」里。每一项读数都画成条并把数字标在旁边；机器没报的读数写成「未知」而不是画成 0——磁盘是最要紧的那个例子，因为「已用 0 GiB」是服务端从未做出过的断言。磁盘条在可用空间低于固定的 5 GiB 时转为警告色，而不是按百分比：Runner 需要的是放下一份 essentials 镜像加两个 conda 环境的余地，那是一份与磁盘多大无关的绝对量。「更新于」带上采样时间，因此一条不再更新的读数是可以看出来的。

昇腾卡在同一个折叠区里一行一张：名称、健康状态、已用/总显存、AI Core 百分比、温度、功率。沙箱打不开的卡会标出驱动给出的原因，原文照显。勾选框就是这台机器的 `npuDevices` 选择；不可用的卡在未勾选时不能勾，已经勾上的可以取消，因为移除一张卡不需要判定，加入一张才需要——`PUT /api/runners/:id/npu-devices` 用的是同一条规则。这份清单来自 `GET /api/runners/npu`，所有机器共用一次读，而不是按机器记录各读一次，这样一次失败不会把机器列表一起带下去；并且在按下「保存勾选」之前不写入任何东西：勾选是草稿，「放弃修改」把它丢掉。

SSH 机器还可以用宿主机自己的 `~/.ssh/config` 来填。选一条会走 `GET /api/remote-hosts/ssh-config?alias=` 解析，然后把结果抄进本应用自己的字段——主机名、端口、用户、私钥文件。抄这一下才是重点：产品此后**不再**读 `ssh_config`，所以表单上显示的就是将来会用的。API 所在的机器读不到的私钥文件会被如实报出来，而不是悄悄从表单里消失。

登记表单和凭据表单都把私钥当成**路径**，因为要读它的是 API 所在的机器；两处都提供浏览那个机器文件系统的入口——`GET /api/remote-hosts/key-files?path=&offset=`。浏览的是哪台机器值得说清楚：是 **API 所在的机器**，既不是浏览器，也不是远程目标机。列目录是分页的、一层一层下去的，不做过滤，因为某个路径下是 NFS 还是别的挂载，从这里看不出来。

远程页下方是「哪些机器可以被项目使用」，它对应当前项目自己的 `runnerIds`。这是一条完整名单而不是默认值的提示：空数组是一个明确的决定（谁都不许，包括本机），而列表为空的历史项目按老字段 `remoteRunnerHostIds` 解释，那时本机是隐含可用的。名单只列出真正能跑的机器——本机恒可用，远端机器要就绪，并且 `direct` 有地址和令牌、`ssh` 的平台是 Linux（部署出去的那份 Runner 是 Linux 的）——因为给一台跑不了的机器一个勾选框，只会换来一次跑到最后一步才失败的运行。不可用的机器仍然留在上方的 Runner 列表里，它为什么不可用在那里是看得见的。每次勾选都写入整份名单，写完再从服务端重读一遍，这样服务端拒绝的 id 不会留在界面上。

## 6. 开发与测试

```bash
pnpm --filter @sciencediscovery/desktop dev      # 127.0.0.1:5174，/api 与 /health 代理到 4310
pnpm --filter @sciencediscovery/desktop test     # tsx --test tests/*.test.ts
pnpm --filter @sciencediscovery/desktop build    # -> apps/desktop/dist
pnpm --filter @sciencediscovery/desktop exec vite preview   # 构建产物跑在 4174，同样代理
```

`localStorage` 按 origin 隔离，所以 token 每个前端都要注入一次：首次打开 `http://127.0.0.1:5174/#token=<token>`。token key 与 `apps/web` 共用，同 origin 下不需要重复注入。

要让这个应用占用根路径而不使用内置路径，用 `SCIENCE_AGENT_WEB_DIR=apps/desktop/dist` 重启即可；静态目录在启动时读取。

测试覆盖传输层（bearer header、401 归类、SSE 分帧，包括注释帧和拆分 chunk）、reducer（思考与正文折叠、snapshot 与 delta、截断 snapshot、终态封口、各类计数、权限请求与答复、工具 trace，以及折叠行「用时」所依据的那两个时间——记下之后不会被后来的快照挪动）、重放层（把一份日志折成收口状态、重建的三种锚点，以及哪些 run 值得留——空日志不值得，回答之前就失败的 run 保留状态条但不隐藏已存储消息）、transcript 合并本身（重放的 run 就地顶替自己那条回答、没有重放的 run 保留持久化回答、没有回答的 run 跟在开启它的消息之后、重放里没被答复的授权渲染为不可点、直播中的 run 排在最后、刚发出的消息先立刻画出自己、run 的占位行则等到那一拍之后、唤醒通知不画卡片但那次 run 仍锚在它发生的位置）、折叠本身（运行时写「正在思考」、结束写「用时 …」、只有模型真的在工作时那一行才转圆环而排队和结束时都不转、没有跨度时退回状态词、思考与工具调用在折叠内、未答复的授权或正在运行的工具调用那句话在折叠外）、工具卡的两个纯函数层（主字段按名字而不是按位置选取、单个参数显示为裸值而不是 JSON、带标记的结果拆成多节且标记前的文字留作残余节、调用失败时残余节标注为 Error、Runner 占位符被丢弃而不是当成数据显示）、工作区文件树（每段一层、同名目录不在同一父级下重复、目录排在文件前并按名字排序、目录的计数递归到底、空段与多余的斜杠被丢掉）、面板宽度的换算（拖拽方向、上下界、窗口窄到装不下两列、以及给 transcript 留出最小宽度的天花板）、页签放置规则、启动判断（空目录、已有默认不被改写、默认指向已删除 profile 时被替换）、侧栏的最近排序、启动时恢复哪个 Session（最近使用的那一个；已经有 Session 打开时不替换）、分子结构的格式判断（后缀、媒体类型、嗅探三者的优先级与 `.cif` 的两种解析器）、现在的设置界面（三个分组下的五个页面、「通用」只有语言选择、白名单输入框按条目解析——换行与逗号都算分隔、空行丢弃、网络与远程页不再拥有的词汇——允许内网与回环地址、出站路由、Runner 的「测试连接」、添加模型表单字段下没有说明且三个按钮按「测试、保存、取消」排列——调用方自带退路时没有取消、输入区只有模型 pill 与回形针而中间没有「会话配置」）、执行机器的取值换算（两种主机密钥失败、目的地址、可达性、可用性、本机不出现在机器卡片里、可用名单与勾选）、机器资源的呈现（机器没报的读数写成未知、磁盘在固定可用空间下限转警告色、NPU 卡不能新增但可以移除）、语言 store（默认中文，除非用户选过别的；一次切换会覆盖 `TEXT` 的每个顶级分节，包括其中的函数；订阅者在真正变化时只触发一次，无变化时一次都不触发；「通用」同时提供两种语言并选中正在生效的那个），以及输入区的模型 pill 与回形针。

`pnpm build` 会为结构浏览器单独产出一个约 3.2 MB 的 chunk（gzip 后约 880 kB），主包约 500 kB；只有真正打开结构文件时才会下载前者，所以构建输出里的这个大 chunk 不是启动成本。
