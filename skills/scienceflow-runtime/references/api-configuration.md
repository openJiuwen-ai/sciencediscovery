# Private model API configuration (ScienceFlow 0.2.x)

**Do not keep real keys in the Skill, `.git`, release ZIP, user-facing text, or task artifacts.**

## Recommended split

1. Public: `config/api.env.example` (names and placeholders only).
2. Private: `$HOME/.config/scienceflow-runtime/api.env` with `chmod 600`.
3. Runtime upstream: `~/.config/scienceflow/models.json` generated by `scripts/configure_api.py`, also `chmod 600`. Current upstream's registry supports `version`, `models`, stage-specific `endpoints`, `defaults`, and `use_proxy`. This intentionally follows upstream `docs/examples/models.example.json`.

Example private env file (replace placeholders on your machine):

```dotenv
SF_MODEL=your-model-id
SF_BASE_URL=https://your-gateway.example/v1
SF_API_KEY=your-secret-key
SF_USE_PROXY=false
# Optional distinct feedback model/endpoint:
# SF_FEEDBACK_MODEL=another-model-id
# SF_FEEDBACK_BASE_URL=https://another-gateway.example/v1
# SF_FEEDBACK_API_KEY=another-secret-key
```

```bash
python3 "$SKILL_DIR/scripts/configure_api.py" --env-file "$HOME/.config/scienceflow-runtime/api.env"
```

This tool generates the model registry and does not attempt an API call. Model availability must be verified with your deployed provider and selected version.

## OpenAI-compatible gateway requiring Authorization

Most OpenAI-compatible SDKs construct `Authorization: Bearer <api_key>` from their API key field. If the gateway's `Authorization` value is the *actual* access token, use it for `SF_API_KEY` rather than a dummy `sk-1234`. If your provider requires **two independent credentials** (SDK `api_key` plus a different fixed `Authorization` header, or any custom `X-...` header), the public upstream sample does **not** document an arbitrary headers field. Do not invent a `headers:` key and assume it works. Confirm that your pinned ScienceFlow revision supports extra headers, or configure a trusted gateway/reverse proxy which injects the extra header. A custom transport patch must be version-pinned and tested.

## Proxy notes

`SF_USE_PROXY=true` maps to `use_proxy: true` in the registry and requests provider proxy behavior if supported by the pinned upstream. `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` remain transport environment settings. **Do not globally enable proxy**; local company gateways may need `NO_PROXY` and upstream's config may take priority. `SFCTL_KEEP_PROXY=1` applies to an older external `sfctl.py` integration and is not the default here.

## Legacy releases

Old versions used a `llm_proxy.yaml` with `agent.code/feedback.models`, `api_keys`, and `base_urls`, and an `.env` file inside the cloned repo. Treat that as a separate version-specific procedure. Do not write a YAML using blind `sed` substitution of secrets (special characters can corrupt YAML). Prefer a private external configuration file or upstream-supported environment interpolation, and never include that generated file in a public archive.
